# 自动化测试与 GitHub Actions

本项目的自动化测试使用 Python 和 Node.js 自带的测试能力，不需要安装第三方依赖。GitHub Actions 工作流文件是 [`.github/workflows/tests.yml`](../.github/workflows/tests.yml)。它已经定义好触发条件和检查步骤；是否在 GitHub 上实际通过，要以 Actions 页面中触发后的运行记录为准。

## 当前测试覆盖范围

Python 测试由 `python -m unittest discover -s tests -v` 发现并执行，当前覆盖三类内容：

- `tests/test_playlists.py` 和 `tests/test_m3u8_create.py` 覆盖 M3U8 上传解析、URL 列表生成、集数偏移、中文和特殊字符编码，以及相关页面/下载响应。
- `tests/test_privacy.py` 覆盖临时 SQLite 数据库中的访问密码哈希、密码校验和会话密钥轮换。备份面板测试也会在临时数据库中验证导出、导入和目录替换。
- `tests/test_backup_connection.py` 和 `tests/test_m3u8_create.py` 会启动项目自己的 `ThreadingHTTPServer`，绑定 `127.0.0.1` 的临时端口，再用 `http.client` 发起真实的本机 HTTP 请求。因此这部分检查包含本地 socket、路由、状态码、响应正文和 SQLite 之间的集成路径。

Node 测试由 `node --test tests/*.test.mjs` 执行，目前文件是 `tests/backup_client.test.mjs`。它检查 `static/backup-client.js` 中的备份地址解析、鉴权、无备份、超时、网络错误、上传和刷新判定。测试通过注入 `fetchStub` 模拟 `fetch` 响应，并不连接真实网络。

这些检查不操作真实浏览器 UI，不播放实际视频，也不连接独立部署的云端 JSON 备份服务器。HTTP 集成测试只访问当前进程里的本地服务；Node 测试只验证备份客户端逻辑和模拟响应。

测试日志中可能看到两类容易误读的输出：

- `test_import_failure_returns_readable_error_instead_of_dropping_connection` 会故意注入 `RuntimeError("boom")`，验证服务把异常转换为可读的 500 JSON 错误。服务端日志出现对应 traceback 是这条失败路径测试的一部分；应以最后的 `Ran ...` 和 `OK` 以及进程退出状态判断整套断言是否通过。
- 本机 Python 3.14 的基线运行中出现了 SQLite 连接未关闭的 `ResourceWarning`。它属于资源管理提示，当前 24 个测试断言仍全部通过；CI 日志会保留这些提示，供后续排查。

## 工作流和 Jenkins 的对应关系

| GitHub Actions 配置 | 用 Jenkins 的概念理解 |
| --- | --- |
| 整个 `Tests` workflow | 一条 Pipeline |
| `jobs` / `steps` | 每个 job 有独立执行环境，job 内的 steps 按顺序执行 |
| `push`、`pull_request`、`workflow_dispatch` | SCM webhook 触发，外加手动构建 |
| `jobs.python-tests` 的 Python 3.10/3.14 matrix | 同一测试阶段在两个工具链版本上的并行构建；`fail-fast: false` 会让两个版本都跑完 |
| `jobs.node-tests` | 独立的 Node.js 24 构建/测试 job |
| `runs-on: ubuntu-latest` | Jenkins agent 标签；使用托管 Ubuntu 执行器 |
| `actions/checkout` | 检出构建工作区 |
| `setup-python`、`setup-node` | 选择构建 agent 上的运行时版本 |
| `Run ... tests` | shell 构建步骤；命令保持和本地测试一致 |
| `timeout-minutes: 10` | 构建超时 |
| `tee` 加日志上传步骤 | 控制台输出加构建产物归档；`if: ${{ always() }}` 使失败时也尝试归档 |
| `permissions: contents: read` | 构建令牌只读访问仓库内容 |

工作流不执行依赖安装、缓存、覆盖率、浏览器测试或额外报告库，因为当前测试只使用 Python/Node 内置能力。Python 的两个矩阵 job 和 Node job 各自独立检出仓库并运行，Python 日志 artifact 名称包含版本号：`python-tests-3.10-log`、`python-tests-3.14-log`；Node 日志 artifact 名称是 `node-tests-24-log`，都保留 7 天。

`tee` 前的 `set -euo pipefail` 和命令中的 `2>&1` 会把标准输出、标准错误同时写入日志，并保留测试命令的非零退出状态。这样测试失败时 job 仍然标红，但后续 `always()` 上传步骤可以提供完整日志。

`workflow_dispatch` 的 `Run workflow` 按钮通常要等工作流文件进入默认分支 `main` 后才会在 Actions 页面显示；工作流文件所在的功能分支仍可先通过 push 或 pull request 触发检查。无论使用哪种触发方式，都不要把“工作流文件已经提交”当成“GitHub 运行已经通过”。

## 查看失败步骤和下载日志

1. 打开仓库的 **Actions**，选择 **Tests**，再打开对应的 workflow run。
2. 在 run 页面分别进入 `Python 3.10 tests`、`Python 3.14 tests` 或 `Node.js 24 tests`，展开失败的 `Run ... tests` 步骤，先查看控制台输出。
3. 回到该 run 的 **Summary**，在 **Artifacts** 中下载对应的 `*-log` 压缩包。测试命令失败时，上传步骤仍会执行；如果日志文件确实生成，就可以从 artifact 中查看完整的 stdout/stderr。

## 本地运行

在项目根目录执行：

```bash
python3 -m unittest discover -s tests -v
node --test tests/*.test.mjs
```

两条命令分别对应 CI 中的 Python 和 Node job。它们不需要先执行 `pip install` 或 `npm install`。修改工作树后还可以检查补丁格式：

```bash
git diff --check
```

## 添加测试文件

添加 Python 测试时，在 `tests/` 下创建 `test_*.py`，使用 `unittest.TestCase` 和 `test_` 开头的方法。例如：

```python
import unittest

from anime_vault.playlists import parse_m3u8_upload


class PlaylistValidationTests(unittest.TestCase):
    def test_rejects_wrong_extension(self) -> None:
        with self.assertRaises(ValueError):
            parse_m3u8_upload(
                "episodes.txt",
                b"#EXTM3U\nhttps://example.com/1.mp4",
            )
```

测试需要临时数据库或本地服务器时，应在 `setUp` 中创建，在 `tearDown` 中关闭并清理，避免影响其他用例。`unittest discover` 会自动发现符合命名规则的文件和方法。

添加 Node 测试时，在 `tests/` 下创建 `*.test.mjs`，使用 `node:test` 和 `node:assert/strict`。如果被测逻辑需要网络请求，沿用现有测试的方式注入假的 `fetch` 实现，用固定响应覆盖成功、失败、超时等分支；不要让单元测试依赖外部云端服务。CI 中的 `tests/*.test.mjs` shell 展开会自动包含新的测试文件。

这个示例沿用现有播放列表测试的无效扩展名场景。新增用例后，先在本地执行对应命令，再提交包含测试文件的变更，GitHub Actions 会自动发现并执行它。
